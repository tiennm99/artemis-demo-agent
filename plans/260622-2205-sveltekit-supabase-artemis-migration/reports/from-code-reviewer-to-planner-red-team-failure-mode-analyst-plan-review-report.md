## Finding 1: Cutover Has No Executable Data Migration Path
- **Severity:** Critical
- **Location:** Phase 7, section "Implementation Steps"
- **Flaw:** The plan says to "migrate or seed demo data intentionally" and then archive/remove the old runtime, but it never defines export, transform, backfill, ID mapping, validation totals, dual-write window, freeze window, or restore procedure for existing SQLite data.
- **Failure scenario:** A preview Supabase project is seeded with example rows, Phase 7 archives `server.py`, and live reports, marketplace pending rows, notifications, and audit history in the current SQLite DB never move. Worse, a stale browser or local cache can still POST a partial shared state during migration and wipe current SQLite tables before export.
- **Evidence:** `phase-07-validation-and-cutover.md:28` requires migration/seed only at a high level, `phase-07-validation-and-cutover.md:106` says compare against baseline without a data migration mechanism, `phase-07-validation-and-cutover.md:116` allows legacy archive/removal after validation, `README.md:44` says SQLite is the shared multi-browser submission store, and `server.py:509` to `server.py:531` shows `import_state()` deletes every major table before reinserting caller-provided lists.
- **Suggested fix:** Add a dedicated data migration phase or pre-cutover gate: freeze writes, export SQLite rows, transform payloads to Supabase rows and storage objects, preserve legacy IDs in mapping columns, verify counts/checksums per table, run rollback restore from SQLite export, then cut over.

## Finding 2: Auth And Admin Model Is Still An Open Question But Later Phases Depend On It
- **Severity:** Critical
- **Location:** Plan, section "Open Questions"; Phase 4, section "Implementation Steps"
- **Flaw:** The plan leaves the login method and admin sharing unresolved while Phase 4 and Phase 7 require Supabase login, scoped admin roles, and protected admin routes. Current behavior is domain/password self-registration plus localStorage fallback, not a Supabase Auth account model.
- **Failure scenario:** Implementation chooses email/password Supabase Auth without mapping existing domain identities. Existing users cannot recover their domain history, `artemis_8920` is not migrated into an admin role, or the old client-side admin assumption gets reintroduced. A non-admin can still call admin mutation endpoints if server-side role checks are not designed before route work starts.
- **Evidence:** `plan.md:121` to `plan.md:124` leaves login/admin scope undecided, `phase-04-domain-routes-and-server-actions.md:100` to `phase-04-domain-routes-and-server-actions.md:103` assumes Supabase login/profile/domain flow, `phase-04-domain-routes-and-server-actions.md:146` to `phase-04-domain-routes-and-server-actions.md:149` requires scoped admin behavior, `app.js:1554` to `app.js:1592` shows current domain/password login with local fallback, `app.js:541` to `app.js:542` hardcodes admin to `artemis_8920`, and `server.py:646` to `server.py:649` trusts an admin PATCH request body actor instead of a server session.
- **Suggested fix:** Decide auth before Phase 3: exact Supabase provider, domain-to-profile mapping, admin seed/migration for `artemis_8920`, session cookie handling, and server-only role lookup. Make route implementation block on that decision.

## Finding 3: Storage Upload Flow Allows Orphans And Forged Object Paths
- **Severity:** High
- **Location:** Phase 3, section "Architecture"
- **Flaw:** The upload model says the browser uploads to Supabase Storage after a draft row or upload intent, but it does not define signed upload URLs, upload-intent expiry, object finalization, DB/storage transaction ordering, owner-path enforcement, or orphan cleanup.
- **Failure scenario:** A user starts a listing upload, the object reaches Storage, and the server action fails before metadata commit. The private bucket fills with unreachable objects. A hostile client can also guess `{profile_id}/{record_id}/{file_name}` paths unless Storage policies validate ownership against a server-created intent, not just a path convention.
- **Evidence:** `phase-03-supabase-data-auth-storage.md:61` to `phase-03-supabase-data-auth-storage.md:70` describes browser direct upload plus later metadata storage, `phase-03-supabase-data-auth-storage.md:107` to `phase-03-supabase-data-auth-storage.md:110` only lists size/MIME/path conventions, `phase-03-supabase-data-auth-storage.md:157` only says validate MIME and file size, `app.js:1399` to `app.js:1428` shows current image handling is base64 DataURL compression in the browser, and `server.py:45` to `server.py:66` stores image text in lost/found rows rather than object references.
- **Suggested fix:** Specify an upload-intents table with owner, record type, record ID, object path, expiry, status, and cleanup job/manual operation. Use signed upload URLs or strict Storage policies tied to authenticated user and intent rows, then finalize metadata server-side.

## Finding 4: Match Notifications Can Be Lost Or Duplicated
- **Severity:** High
- **Location:** Phase 4, section "Implementation Steps"
- **Flaw:** The plan says server actions will compute candidate matches and create notifications, but it does not require one transaction, idempotency keys, unique match pairs, or retry behavior between report creation, match candidate persistence, and notification creation.
- **Failure scenario:** A user double-submits a lost report, reloads during the action, or two users report matching items at nearly the same time. Supabase stores duplicate match notifications, or stores the report and match candidate but fails before owner/finder notifications. The user sees no radar notification even though the DB contains a match.
- **Evidence:** `phase-04-domain-routes-and-server-actions.md:105` to `phase-04-domain-routes-and-server-actions.md:110` assigns create report, compute matches, and create notifications to server actions without transaction/idempotency requirements, `app.js:946` to `app.js:949` shows current lost flow creates notifications after a client-side match, `app.js:1354` to `app.js:1395` creates two client-side match notes and posts them independently, `server.py:441` to `server.py:487` creates match suggestions only, and `server.py:345` to `server.py:363` inserts each notification as a new row without a uniqueness key.
- **Suggested fix:** Define a single server-side workflow: insert report, upsert canonical match pairs with unique `(source_type, source_id, matched_type, matched_id)`, upsert deterministic notification records, and return the user-facing result from that transaction.

## Finding 5: Marketplace Care Is A Lost-Update Trap
- **Severity:** High
- **Location:** Phase 3, section "Architecture"; Phase 4, section "Implementation Steps"
- **Flaw:** The plan names `marketplace_interests` and "express interest/care" but does not require a unique `(listing_id, profile_id)` constraint, atomic toggle semantics, or idempotent owner notifications. Current behavior is mutable `careCount` plus `caredBy` array pushed through whole-item updates.
- **Failure scenario:** Two users care the same item at the same time. Both load count 0, both write count 1, and one interest disappears. Or one user double-clicks and creates multiple owner notifications. In Supabase/Vercel server actions this becomes a production race instead of a local demo quirk.
- **Evidence:** `phase-03-supabase-data-auth-storage.md:43` to `phase-03-supabase-data-auth-storage.md:46` lists `marketplace_interests`, `phase-03-supabase-data-auth-storage.md:94` to `phase-03-supabase-data-auth-storage.md:99` lists indexes but no unique care constraint, `phase-04-domain-routes-and-server-actions.md:111` to `phase-04-domain-routes-and-server-actions.md:116` includes the care action, `app.js:1897` to `app.js:1917` mutates `caredBy` and `careCount` client-side before sending an update, and `server.py:280` to `server.py:311` overwrites the marketplace payload with caller-provided updates.
- **Suggested fix:** Model care as an insert/delete on `marketplace_interests` with unique `(listing_id, profile_id)`. Derive counts from the table or maintain them with a DB function/trigger. Generate owner notification from the same idempotent toggle path.

## Finding 6: Lost/Found Admin Moderation Is Planned But Not Testable Or Backed By Current Contracts

## Finding 7: Cutover Drops The AgentBase Runtime Contract
- **Severity:** Critical
- **Location:** Phase 6, section "Architecture"; Phase 7, section "Success Criteria"
- **Flaw:** The migration target routes list only SvelteKit product pages. It omits `/health` and `/invocations`, while Phase 6 removes Python/SQLite from production and Phase 7 can archive `server.py` and `Dockerfile`. - **Evidence:** `plan.md:29` to `plan.md:38` lists target routes without `/health` or `/invocations`, `phase-06-deployment-and-operations.md:47` to `phase-06-deployment-and-operations.md:54` says no Python/SQLite in production, `phase-07-validation-and-cutover.md:68` to `phase-07-validation-and-cutover.md:72` allows archiving `server.py` and `Dockerfile`, `phase-07-validation-and-cutover.md:139` requires no SQLite/Python production path, `README.md:46` to `README.md:50` documents `/health` and `/invocations`, `docs/project-workflow-tech-stack.md:158` to `docs/project-workflow-tech-stack.md:162` says `/invocations` is the main compatibility hook, and `server.py:552` to `server.py:553` plus `server.py:612` to `server.py:628` implement those endpoints today.
- **Suggested fix:** Either explicitly deprecate AgentBase with stakeholder signoff, or add SvelteKit `+server.ts` handlers for `/health` and `/invocations`, include them in smoke tests, and document traffic routing from the old AgentBase endpoint.
